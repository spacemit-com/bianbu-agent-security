## 1. 先分清三种环境

| 环境 | 目的 | 代码/状态位置 | 使用入口 |
|---|---|---|---|
| 本地两仓源码 | 修改代码、单元测试、阅读与构建 | 相邻 Security/Runtime checkout | 当前仓测试、Runtime `uv` 环境 |
| Worker 源码开发实例 | 开发验证与定向调试 | 以设备实际路径为准；旧资料常见 `/home/bianbu/impl/bianbu-securityd` | testkit 独立启动脚本；明确 system/session bus |
| Worker DEB 安装实例 | 验证安装产物与服务协作 | Security `/usr/lib/bianbu-securityd`；Runtime `/usr/lib/bianbu-agent-runtime` | systemd 服务及包安装流程 |

默认目标平台是 K3 riscv64，常用 Worker `10.0.90.243`；历史报告中的 `10.0.91.146` 是另一台现场设备。两台的版本和热修复记录不能互相替代。本次编写未连接任一设备。

## 2. 接手当天先采集现场，不先重装

用已有 SSH key 登录，访问方式与权限由交接双方移交；本目录不复制密码或模型密钥。以下在目标机执行，默认运行用户为 `bianbu`，其他用户替换 unit 实例名。

```bash
uname -m
cat /etc/os-release
dpkg-query -W bianbu-agent-securityd bianbu-agent-runtime
systemctl --no-pager --full status bianbu-securityd.service bianbu-agent-runtime@bianbu.service bianbu-security-webui.service
systemctl cat bianbu-securityd.service
systemctl cat bianbu-agent-runtime@bianbu.service
systemctl cat bianbu-security-webui.service
busctl --system introspect io.bianbu.Security /io/bianbu/Security io.bianbu.Security
ss -ltnp
stat /run/bianbu/securityd.sock
```

记录：设备、内核、包版本、unit 的 ExecStart 和 drop-in、socket、端口、数据目录、是否有热修复。输出可能含环境配置，归档前去掉凭据。HTTP 端口常见 9899；WebUI 历史使用过 8787/8788，按真实配置，不硬编码报告里的端口。

Runtime 健康检查可从 `curl -fsS http://127.0.0.1:9899/api/health` 开始；受保护入口使用现场已配置认证。健康响应不能替代创建会话、完成真实 Run 及安全测试。

## 3. 源码开发环境

在开发机从 Security 仓根目录设置路径：

```bash
export SEC_REPO="$PWD"
export RUNTIME_REPO="$(cd ../bianbu-agent-runtime && pwd -P)"
export BIANBU_SECURITYD_HOME="$SEC_REPO/impl/bianbu-securityd"
export BIANBU_SECURITY_CLIENT_DIR="$BIANBU_SECURITYD_HOME/client"
```

依赖按两个仓的构建和锁文件安装。Security 需要系统 D-Bus/PyGObject、cryptography 等；Runtime 使用自己的 uv/虚拟环境。不要把 Python 3.12/3.14 的 C 扩展直接混用。包构建当前要求以 `debian/control` 的 Python 3.14 等依赖为准。

如需本地会话调试，使用同一用户会话且已有可用 session bus：

```bash
SECURITYD_HOME="$BIANBU_SECURITYD_HOME" SECD_BUS=session   BIANBU_SECURITY_TEST_ADMIN=1   bash "$SEC_REPO/testkit/scripts/start-bianbu-securityd.sh"
export BIANBU_SEC_SESSION=1
cd "$RUNTIME_REPO"
./run.sh --with security
```

这是开发入口。安装服务不使用 `BIANBU_SECURITY_TEST_ADMIN=1` 或临时 session bus。已有正式实例时，先确认不会争用 socket/数据库/端口。若 Runtime 报缺少外部 Memory SDK/服务或模型资源，应按其安装依赖补齐，不通过关安全让启动看似成功。

## 4. 已安装服务的更新顺序

开始前保留旧包、记录现场，备份配置与数据库的一致快照。SQLite 活跃时用 backup API/工具，或停掉写入者再复制 DB/WAL；不能只拷一份正在写的 `.db`。

在已准备好两份匹配目标架构的包后，以下为操作顺序。先为变量填写本次实际包路径，检查包名、版本和架构：

```bash
: "${SECURITY_DEB:?请设置 Security deb 绝对路径}"
: "${RUNTIME_DEB:?请设置 Runtime deb 绝对路径}"
dpkg-deb -f "$SECURITY_DEB" Package Version Architecture
dpkg-deb -f "$RUNTIME_DEB" Package Version Architecture
sha256sum "$SECURITY_DEB" "$RUNTIME_DEB"
sudo apt install "$SECURITY_DEB"
sudo apt install "$RUNTIME_DEB"
sudo systemctl restart bianbu-securityd.service
sudo systemctl restart bianbu-agent-runtime@bianbu.service
sudo systemctl restart bianbu-security-webui.service
```

包安装脚本可能已经启动/重启服务；安装后仍需确认最终进程来自新路径/版本。Security 重启可能影响 Runtime 依赖链，现场应在维护窗口执行并保存活动任务状态。

检查顺序：securityd active 且接口存在 → Runtime active → 新 Worker/新 lease → 新会话完成 → normal 下拒绝/脱敏断言 → 审计查询 → 原模式与策略恢复。详细标准见第 6、9 篇。

## 5. 构建、demo 与生产配置

Security 在已装好构建依赖的目标架构环境，从 S 根目录运行 `dpkg-buildpackage -us -uc -b`。默认 `DEB_DEMO=1`；生产配置构建应显式 `DEB_DEMO=0 dpkg-buildpackage -us -uc -b`，并准备完整的签名和认证条件。

| 项目 | 当前 demo 包选择 | 产品化发布需要 |
|---|---|---|
| Security 代码签名 | drop-in 设置 `BIANBU_SECURITY_CODESIGN=off` | 省略 demo drop-in，配置受信公钥及撤销流程 |
| Security WebUI | drop-in 设置 demo，免 Bearer Token | 省略 demo drop-in，配置正式 token/认证与访问边界 |
| Runtime manifest | 默认构建可生成 development self-signed manifest | 通过 `SECURITY_MANIFEST_DIR` 提供符合构建校验的签名资产 |
| Runtime manifest version | 与 Debian 包版本独立 | 发布时按规则递增，避免信任声明回滚 |

Runtime 构建以 R `debian/rules` 为准：默认从构建环境生成开发自签 manifest；若显式传入 `SECURITY_MANIFEST_DIR`，走校验已有资产的路径。不要把 `ALLOW_UNSIGNED_RUNTIME_PACKAGE=1` 当生产构建办法。

K3 原生构建使用板端工具链。x86 向 K3 交叉编译 C/C++ 产物按仓库 AGENTS 的 SpacemiT 工具链约定；涉及本地 AI 栈时遵循 ggml-spacemit / spacemit-ep，不改用通用实现作为交接默认依赖。

## 6. 发布流程

1. 固定两仓提交，记录工作区是否干净、构建参数、包版本、manifest 版本。
2. 跑本次改动对应回归与安装验证，归档日志和包 SHA-256。
3. 更新 changelog、交接状态及兼容性说明；没有新硬协议需求，不自动提高 Runtime 对 Security 的最低版本。
4. 按各仓授权提交/推送。Security 发布 tag 必须是 `bianbu/<版本号>`，与 changelog 顶部一致。
5. 创建 Security tag 前展示完整名称并确认；使用附注 tag，指向发布提交，推送后核对远端目标。不要使用 `v<版本号>`。
6. 当前 main 工作树未发现根级 GitLab CI 配置；标签触发是仓库发布约定，实际 job/流水线配置由 GitLab 和发布维护人核实，不能仅凭 push 成功宣称构建发布成功。

本地发布证据入口是 `S/impl/bianbu-securityd/.ci/run_tests.sh`，不是 S 根目录的 `.ci/`。strict 与商用门禁见第 6 篇；MVP 完成不等于已执行全部组织级产品发布流程。

## 7. 回滚与恢复

回滚前先保留故障日志、新包、配置及数据快照，查明是否发生 schema/manifest 版本变动。只安装旧包可能被 manifest 防回滚拒绝，也可能读不懂新数据库；必须使用经过验证的版本与数据恢复方案。

执行顺序为停止 Runtime/相关写入者 → 按方案恢复兼容的代码、配置与数据 → 启动 Security → 启动 Runtime/WebUI → 创建新 Worker 并重复验收。不要恢复旧 lease 来冒充新的已授权进程。

日常升级不执行清理全量安全数据。reset 仅用于明确的重置场景，先阅读[数据清理说明](../clear-security-data.md)，预览影响并备份；它不是“任何故障先执行一次”的修复手段。
