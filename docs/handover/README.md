## 1. 本次交接什么

**Agent Security 当前 MVP 已完成。本次交接的目标，是让接手同事理解已有实现，能独立维护、定位问题、验证修改和交付版本。** 后续性能、体验和维护性改进列为优化建议；新的产品能力需要重新确认需求与验收标准，不作为本次 MVP 的欠账。

这不是整个 Agent OS 的交接。范围包括两个仓库中的 Security 相关代码、接口、配置、测试和发布流程：

| 仓库 | 交接范围 | 一句话职责 |
|---|---|---|
| `bianbu-agent-security`，当前仓库 | `impl/bianbu-securityd/`、`testkit/`、`debian/`、安全设计及验收文档 | 决定能否执行、采用什么策略，并保存安全证据 |
| 相邻 `bianbu-agent-runtime` | `bianbu_agent/security/`、安全插件、模型/工具边界、管理 API、Worker 执行及相关测试 | 在真实 Agent 执行链路中落实安全决定 |
| 外部协作项 | 控制台源码、Memory、模型服务、桌面与平台镜像 | 记录依赖和协作入口；不默认转交这些产品的全部维护职责 |

旧资料里的 PA/personal-agent，在本次交接中指当前 `bianbu-agent-runtime` 的历史名称。当前正式接入使用控制进程与受管 Worker，不能把旧单进程启动方式直接套用到安装包。

## 4. 交接时特别容易混淆的事项

| 旧理解 | 当前应怎样理解 |
|---|---|
| 安全代码都在 Security 仓 | 策略在 Security；真正的模型、工具和 Worker 执行边界还在 Runtime |
| `.bianbu-agent/plugins/` 是唯一插件源码 | 当前内置安全插件源码在 `R/resources/plugins/bianbu.security/` |
| hook 目录只能有 `hook.py` | 当前安全插件是 `hook.json` 声明命令，执行 `scripts/*.py`；旧约束属于旧 loader 形态 |
| 所有安全请求都走 D-Bus | 管理与启动控制走 D-Bus；受管 Worker 判权、DLP、Token 等走带租约身份的 UDS |
| 新建 Agent 默认就是 normal | 当前注册默认 YOLO，验权限/DLP 前要读取并显式设为 normal |
| YOLO 仍执行 DLP、网络限制、Token 限额 | 本基线 YOLO 跳过这些检查，保留身份、沙箱、审计及用量/网络记录；详见第 4 篇 |
| 36 项、573 项或 73 failed 是永久基线 | 都是历史上下文；以当前用例注册、同版本运行报告和逐项失败集合为准 |
| service active、网页可打开就是验收通过 | 还要验证 Worker、真实 Run、安全拒绝及审计证据 |

发现历史文档冲突时，先核对本次锁定的源码与安装资产，再看时间更晚、范围相符的证据。不要悄悄改写旧报告中的历史事实。

## 5. 资料维护约定

接口或行为变动时，至少同步本目录第 4、6、8 篇；部署路径变动同步第 5、7 篇。新增功能应补充“需求来源 → 两仓修改点 → 防回归用例 → 验收证据”。本目录不复制所有旧设计，深层背景通过链接保留追溯。

接手人、支持联系人、交接日期、设备访问权限和后续发布责任在第 9 篇签收时记录。控制台源码所在仓库及其维护人也在该处核实，不能仅凭旧文档中的相邻目录名判断交付齐全。
