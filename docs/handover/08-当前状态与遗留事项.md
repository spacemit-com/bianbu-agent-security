## 1. 交接结论

**当前 Agent Security MVP 已完成，按已有可运行实现交接。** 接手后的第一责任是维护当前行为与两仓兼容，处理实际回归；性能、可观测性、体验和文档一致性可以继续优化。新的业务范围应经过产品确认后开发。

本篇把三类事实分开：当前源码包含什么、历史报告曾验证什么、接手时还应核查什么。没有把“本次写文档未重跑全量”解读为“MVP 没完成”，也不把历史通过自动扩展为新 HEAD/所有设备的通过。

## 5. 可继续优化的方向

以下优先级是维护建议，未代表已批准排期。只有明确负责人和目标版本后才进入开发任务。

| 编号 | 优化建议 | 价值 | 建议验收方式 |
|---|---|---|---|
| O-01 | 启动/接口健康检查统一输出版本、模式、Worker 和数据路径 | 减少“验到旧进程”及路径混用 | 错总线/错 socket/旧服务三类注入均能指出具体失败层 |
| O-02 | 两仓兼容组合的自动化回归 | 避免单仓通过、联合失败 | 固定安装包矩阵，逐项保留 Run/审计与失败集合 |
| O-03 | DLP/UDS 的负载、连接与尾延迟观测 | 提早发现 FD、SQLite 和队列问题 | 固定负载记录 FD/RSS/P50/P95/P99，重复运行可比较；阈值先建立设备基线 |
| O-04 | 网络/模式变更状态展示 | 避免“保存成功”被误解为已执行 | 页面区分保存/执行/待重启/失败，真实后端状态一致 |
| O-05 | normal DLP 输出治理的交互体验 | 保留防泄漏同时改善等待感 | 原文零提前发布，进度与取消可用，首个可见反馈时间有量化对照 |
| O-06 | 文档与案例自动检查 | 减少旧路径、旧 hook 形态和数量过时 | 本目录内部链接零断链，关键路径/命令与当前树一致 |
| O-07 | 现场问题证据归档标准化 | 接手人不依赖原作者记忆 | 每条缺陷具版本、设备、复现、根因、修复、回归和关闭证据 |

## 6. 已记录但需跟踪的现场现象

9 月 16 日 FD 修复现场报告记录过首次预热 `Runtime startup failed: message must not be empty`，正常 Worker 请求重试后恢复；报告明确该轮未修复此冷启动异常。它属于有历史证据的维护跟踪项：接手时在当前版本复现，若仍存在则建缺陷、定位并补回归；若不可复现则记录环境和测试范围，不武断宣称已修复。

同理，旧报告中网络 learning、安装测试路径等失败已有后续调查或修复，不能将所有旧 FAIL 汇总为当前未完成。关闭与否应以时间更晚、版本和范围相符的证据判断。

## 7. 是否还有新的产品需求需要开发

**可能有下一阶段需求，但当前没有在本次交接中确认的新需求清单或开发承诺。** 下面是与现有设计相关、值得向产品提问的候选方向：

| 编号 | 候选方向 | 需要产品先回答 | 立项后怎样定义验收 |
|---|---|---|---|
| N-01 | 从 MVP/demo 转正式产品安全交付 | 目标客户、签名根管理、认证角色、设备访问边界是什么？ | 正式包无 demo drop-in，签名/吊销、认证、升级恢复与发布证据按约定覆盖 |
| N-02 | 多用户/组织/设备的策略治理 | 是否需要跨用户、跨设备集中管理和策略模板？ | 定义隔离边界、角色矩阵、审计归属及并发/规模指标 |
| N-03 | 更细的数据治理 | 是否要新 PII 类型、企业自定义规则、审批、保留周期？ | 每类有正负样本、误报/漏报目标、出口和策略优先级 |
| N-04 | 新执行后端或更强隔离 | 是否实际需要 OCI/容器、多平台隔离？ | 明确目标架构、启动性能、网络/文件边界、生命周期兼容 |
| N-05 | 更全面的网络出口治理 | 是否需要域名持续解析、代理、协议粒度及集中观测？ | 明确 DNS/IPv4/IPv6/代理等边界与允许/拒绝测试矩阵 |
| N-06 | 长期运行、合规和组织验收 | 是否承诺 24/72h、渗透、CA、桌面及正式审批门禁？ | 采用已有证据工具，补齐组织外部证据并实际执行规定时长 |

若产品不增加范围，后续就以维护和优化为主。若增加范围，按“场景/需求编号 → 明确不包含什么 → 两仓职责 → API 与数据变更 → 测试与量化验收 → 发布/回滚”形成新需求，不直接把旧设计里所有展望都当待办。
