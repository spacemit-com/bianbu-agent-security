## 1. 先采证，再改一处

接手人收到“聊天失败/安全不生效”时，先问清：哪个设备、哪个 Agent、哪个 Session/Run、什么时间、normal 还是 YOLO、最近升级了哪一仓。不要先清库或调大权限。

最小记录包括两仓/包版本、Agent ID、Run ID、instance/lease、PID/cgroup、当前策略和错误信息。审计中寻找同一身份和时间段，不能把另一个 Agent 的通过记录当成当前请求证据。

安装态常用只读命令：

```bash
systemctl --no-pager --full status bianbu-securityd.service bianbu-agent-runtime@bianbu.service
journalctl -u bianbu-securityd.service --since '-15 min' --no-pager
journalctl -u bianbu-agent-runtime@bianbu.service --since '-15 min' --no-pager
journalctl -u bianbu-security-webui.service --since '-15 min' --no-pager
busctl --system introspect io.bianbu.Security /io/bianbu/Security io.bianbu.Security
stat /run/bianbu/securityd.sock
ss -ltnp
```

源码会话实例改用正确的 session bus/启动脚本日志，不要查询系统服务后就断言用户会话进程不存在。日志分享前去掉 token、模型凭据和原始敏感载荷。

## 2. 按现象定位

| 现象 | 第一检查 | 可能原因 | 处理与复验 |
|---|---|---|---|
| 网页能开，Run 不完成 | Runtime/Worker 日志和 Run 终态 | Worker 启动、模型记录、MCP、Memory 或安全链路失败 | 按异常链定位；新建会话验证 completed，不只刷新页面 |
| `NameHasNoOwner` / `ServiceUnknown` | 总线类型、服务 owner、unit | Security 未启动或连错总线 | 修复对应实例；启动后 introspect 再发真实请求 |
| `UnknownMethod` | 新源码方法是否存在、运行 PID/ExecStart | 旧进程仍占名或客户端/服务不匹配 | 重启正确服务，确认新签名；不要同时再起第二个实例 |
| 找不到 `bianbu_security_client` | 实际 Python、客户端安装路径 | 环境未发现客户端 | 设置/核对安装路径，确认加载文件来自 Security 包 |
| `dbus` ABI 错误 | Python 版本与 C 扩展版本 | 源码 venv 与系统 D-Bus 扩展不兼容 | 控制面使用系统 helper；Worker 仍直接 UDS |
| `Worker 未通过…lease 身份校验` | 实际 PID/UID/cgroup 与已提交实例 | 旧 lease、错误 namespace、改用子进程代发 | 重建正常 Worker 生命周期；不伪造 lease、不跳过 peer 校验 |
| 冷启动提示 `lease 已过期` | 安装版本、单调时钟修复是否部署、内核启动记录 | 旧版 wall-clock 判定遇 NTP 跳变，或真实超时 | 核查 0.1.32 对应修复；真实超时查启动耗时；不要直接延长所有 lease |
| 授权后仍 DENY | 逻辑 Agent、capability、scope、注册字典 | 配错 Agent、能力未注册、scope 不匹配 | 查实际请求与审计，修正映射/目标；不能只勾“所有权限” |
| 不出现审批或提前执行 | after_model/HITL 与 before_tool 时序 | 中间件读了尚未写入的标记，或映射不一致 | 用 CONFIRM 探针证明审批前零执行 |
| DLP 规则没效果 | 首先读权威模式，再看 findings/action | YOLO、错误 Agent、Runtime 未采用治理结果 | normal 测试；追踪模型/工具真正出口 |
| DLP 报错后低风险工具仍执行 | 错误类型与降级分支 | BLOCK 被混同“连接失败” | 保留 `DLPDenied` 终止语义，补零执行测试 |
| 页面对原文先流式输出后才遮盖 | 模型原始回调与治理发布时机 | 先发出原始 token | 修复发布边界；模型输出回归不能只检查最终结果 |
| Token 配额不触发 | 模式、Session ID、有效限额和累计值 | YOLO 无限额、会话键不一致 | normal 下用独立 Session 验证，切换不清计量 |
| 网络配置成功但行为没变 | effective/apply、当前 backend/instance | 仅保存策略、旧 Worker/采集器、bwrap 需重启 | 走 Runtime 管理链路协调更新；实际连接复验 |
| collector active，事件 0 | 真实请求、注册 PID/cgroup、采集日志 | 活动标志不是记录、旧 registration、权限/内核问题 | 验证新事件落库和身份，不能手工插入事件刷绿 |
| syscall 被拒绝但无审计 | 内核结果、observer、Agent/lease 关联 | 阻断链和采集链不同，采集端未覆盖 | 同时保存 errno 和真实内核事件；检查策略版本 |
| DLP/网络都超时，FD 很多 | Security `/proc/<pid>/fd` 与 DB/WAL 句柄 | SQLite 连接泄漏等资源耗尽 | 查连接关闭修复，定向重复请求，确认空闲 FD 不持续增长 |
| 测试“0 项全通过” | 调用命令和 collected 数 | 运行 `engine.py` 或筛选错 ID | 使用 runner，确认实际集合与退出码 |

## 3. FD 泄漏案例怎样复用

9 月 16 日已有 DLP SQLite 连接泄漏修复。定位步骤：

1. 找到真正的 securityd PID：`systemctl show -p MainPID --value bianbu-securityd.service`。
2. 在具备读取权限的终端统计 `/proc/<PID>/fd`，观察同样请求负载前后及空闲时是否持续增加。
3. 将 FD 目标分类，确认是否大量重复指向 DLP SQLite/WAL，而不是只看总量。
4. 核对安装文件与修复提交；停止泄漏后再做可重复请求和错误 lease 拒绝测试。
5. 服务重启只能临时释放句柄；若代码未修复，负载上来会再次耗尽。

历史证据为 1000 次策略请求成功、FD 27→27，不是要求所有新环境 FD 必须等于 27。验收应比较同环境稳定基线和趋势。

## 4. 遇到配置/数据不一致怎么办

先区分“源代码默认值”“持久化保存值”“运行中的有效值”。例如 YOLO 保留 normal 网络配置但有效值 allow_all，syscall 新策略可能等待 Worker 重启。UI 显示要同时表达保存状态和执行状态。

恢复策略时优先用管理接口写回原值，并按后端需要重建 Worker。不要直接编辑 capabilities/lease 表让状态看起来一致；那会绕过审计与身份约束。

## 5. 常见维护动作的闭环

| 动作 | 完成条件 |
|---|---|
| 修改 Security Python 代码 | 对应单测通过；更新目标文件/包；重启实际 Security 服务；真实请求与审计复验 |
| 修改 Runtime/安全插件 | 定向回归；更新安装资源；重启 Runtime/Worker；确认插件确实从新路径加载 |
| 修改前端 | 找到源仓；修改 contracts/adapter 等；构建后同步 Runtime asset；验证 API 与页面 |
| 修改 systemd/drop-in | daemon-reload + 正确服务重启；核对最终配置及新 PID；不能只查看文件内容 |
| 处理升级失败 | 保留失败日志和新旧包/配置；查 manifest/schema 兼容；按第 5 篇回滚 |
| 清理测试 Agent | 恢复策略/模式，删除测试资源，确认未触及用户真实 Agent/会话 |

## 6. 提交给协作同事的问题应包含什么

给出复现步骤、预期/实际、设备架构、版本组合、Run/Agent 标识、相关日志时间段、当前模式与有效策略、已验证排除项。跨仓问题附“最后成功的边界”：例如 PrepareStart 成功但 CommitStart 拒绝，或 UDS scan 返回 mask 但 SSE 仍有原文。

不要只说“安全坏了”。能指出最后成功的接口，通常就能明确由 Security、Runtime、前端、模型服务还是平台内核维护人继续处理。
