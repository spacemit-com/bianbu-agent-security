## 1. 先理解系统解决的问题

Agent 可以调用工具、读写文件、访问网络和把上下文发给模型。Security 为这些行为提供统一的授权、敏感数据处理和审计；Runtime 把这些检查放在真正发生操作之前，并管理执行进程。

可以用一条规则理解分工：**Security 返回可信决定，Runtime 必须在正确的执行边界落实决定。** 只写策略没有约束 Worker，或只拦住工具却漏掉模型历史消息，都不是完整链路。

## 2. 运行组件

| 组件 | 所属仓库 | 主要输入/输出 | 部署识别 |
|---|---|---|---|
| securityd | S | 管理策略、鉴权、DLP、租约、审计 | `bianbu-securityd.service`；总线 `io.bianbu.Security` |
| Runtime 控制进程 | R | HTTP/API、Agent/Session 管理、Worker 调度、安全管理转发 | `bianbu-agent-runtime@<用户>.service` |
| Agent Worker | R | 模型调用、工具、插件、上下文；携带 instance/lease 身份 | Runtime 创建的受管进程，结合 PID/cgroup 识别 |
| Security 独立 WebUI | S | 查看/配置策略和审计 | `bianbu-security-webui.service`；端口以配置为准 |
| Runtime 内嵌安全页面 | R 中的资源及外部前端构建产物 | 通过 Runtime 安全 API/operation 管理 | `R/bianbu_agent/console/web/security/` |
| 网络/系统调用观测组件 | 两仓配合 | 内核/进程事件关联 Agent、实例和策略版本 | `bianbu-agent-network-learning.service`、`bianbu-syscall-observer.service` 等 |
| testkit | S | 真实 Runtime + securityd 的端到端测试 | `S/testkit/runner.py`；监视台不是产品服务 |

Security 仓内还保留 `runtime/runtime_service.py` 参考生命周期服务。它不是正式 Runtime 的替代品，实际两仓边界是 `io.bianbu.Security.Runtime`，不是 `io.bianbu.Runtime`。

## 3. Worker 启动链路

```text
用户创建会话/发起任务
  → Runtime 控制进程找到逻辑 Agent
  → ExecutionCoordinator 请求 SecurityRuntimeClient.prepare_start
  → securityd 校验 Runtime 身份与 manifest，决定 effective_mode，签发一次性 lease
  → Runtime 按结果选择 host 或 bwrap 后端，创建进程和资源约束
  → Runtime CommitStart 上报 instance_id、PID、cgroup 等执行事实
  → securityd 校验真实进程并提交 lease
  → Worker 携带租约身份通过 UDS 调用安全数据面
  → 停止/异常时回收进程、租约、代理和采集器
```

`requested_mode` 是请求偏好，`effective_mode` 才是 Security 的决定。不要把 fallback 写成“sandbox 起不来就直接裸跑 host”。提交失败要终止对应执行实例并收敛状态。

Lease 是一次启动的限时凭证，不是永久授权。当前版本使用签发时的单调时钟截止时间，避免冷启动 NTP 校时让刚创建的 lease 过期；跨重启 lease 失效，旧记录保留兼容判断。

## 4. 一次模型/工具调用的安全链路

1. Worker 获得当前逻辑 Agent、Session、Run 的上下文。
2. normal 模式下，模型请求中的当前消息、历史、system message 等经过 DLP；Token 预算参与执行控制。
3. 模型返回工具调用时，安全中间件判断是否需要人工审批。审批发生在工具实际执行之前。
4. 工具调用进入能力映射、scope 检查及相关 DLP 边界；DENY/BLOCK 不能被当成普通工具失败后继续执行。
5. 工具结果和模型输出也经过对应治理，再进入后续上下文或对外发布；只清洗输入是不够的。
6. Runtime 将执行结果、错误原因和审计关联起来。定位问题时串联 Agent、Session、Run、instance、lease、PID。

YOLO 是按 Agent 由 securityd 管理的另一套有效行为，详见[功能说明](04-功能与接口说明.md)。检查是否生效时先读取权威模式，不凭网页按钮或环境变量推断。

## 5. 四种身份不要混用

| 身份 | 表示什么 | 排查用途 |
|---|---|---|
| 逻辑 Agent ID | 用户选择的某个专家/Agent；实际值从当前 Agent 列表获取 | 能力、DLP、模式、Token 等策略归属 |
| Runtime 安全身份 | 安装 manifest 中声明的控制面身份，包默认 `com.bianbu.runtime` | 启动授权、可信 Runtime 绑定 |
| instance_id / lease_id | 一次 Worker 执行实例及启动凭证 | 防止旧进程、错误实例冒用身份 |
| PID / UID / cgroup | 操作系统看到的真实进程身份 | UDS peer credential 和已提交 lease 的交叉校验 |

UDS `_require_agent` 使用 `_worker_security_agent_id` 做租约鉴权，业务策略仍返回请求的逻辑 `agent_id`。不要把所有字段统一硬编码成 `com.bianbu.agent`；旧示例中的默认值不是新部署的身份证明。

## 6. 修改责任表

| 改动 | Security 侧 | Runtime 侧 |
|---|---|---|
| 新能力或改能力名 | 字典、别名、判权和管理查询 | 工具映射、能力同步、风险表、确认逻辑 |
| DLP 新类型/动作 | scanner、策略存储、UDS 返回契约 | 模型/工具/Skill 边界、替换结果、错误及前端展示 |
| Worker 新执行后端 | 策略和身份校验、租约结果 | 创建/停止进程、资源及网络约束、恢复和监控 |
| 新接口/字段 | service、客户端、XML/协议、测试 | 适配层、管理 API、调用方和测试 |
| 网络策略或安全模式变化 | 保存策略、计算有效策略和执行状态 | 更新/重启 Worker、采集器与 UI 状态收敛 |
| 审计展示 | 事件结构、存储与导出 | 事件来源、查询转发、可读错误与界面 |
