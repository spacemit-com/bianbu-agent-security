## 1. 技术选型：为什么正则打底而非直接上 NER

目标平台（worker K3 riscv64）只有 `onnxruntime`，没有 spaCy/transformers，装 NER 模型代价不小。而 8 类基线 PII 里 **6 类是结构化的**（手机、身份证、邮箱、银行卡、医疗编号、生物特征标识），正则配校验算法就能做到高召回。

真正需要 NER 的是姓名和地址。当前方案：
- **地址** — 靠"行政区划后缀 + 门牌号"双重约束，正则足够（实测召回 100%）
- **姓名** — 称谓词上下文 + 姓氏表 + 虚词过滤的启发式，如实标低置信度 0.70

NER 做成可插拔后端（`ner_backend` 参数），装得上就启用，装不上优雅降级。这样目标平台先能用，后续接入 NER 不需要改调用方。

## 2. 8 类 PII 与风险级别

| 类型 | 风险级 | 检测方式 | 置信度 | 实测召回 |
|------|--------|----------|--------|---------|
| `name` | L1 | 启发式（称谓+姓氏表）/ NER | 0.70 | 100% |
| `email` | L2 | 正则 | 0.95 | 100% |
| `phone` | L2 | 正则 + 边界断言 | 0.92 | 100% |
| `address` | L2 | 正则（区划+门牌） | 0.85 | 100% |
| `id_card` | L3 | 正则 + GB 11643 校验码 | 0.99 | 100% |
| `bank_card` | L3 | 正则 + BIN + Luhn | 0.96 | 100% |
| `medical` | L4 | 正则（病名/诊断关键词） | 0.80 | 98% |
| `biometric` | L4 | 正则（特征标识词） | 0.82 | 100% |

风险级别不是装饰 —— **DLP-04 用它决定云端调用是否放行**：L3/L4 的 PII 出现在 prompt 里，云端模型调用会被阻断或降级为本地推理。

## 3. 误报控制：三道校验

误报率是这个引擎最难的部分。正则本身很容易过匹配：11 位数字满足手机号形态的太多了（订单号、流水号）。三道校验依次收紧：

### 3.1 第一道 —— 边界断言

```python
_RE_PHONE = re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)")
```

`(?<!\d)` / `(?!\d)` 保证不是长数字串的一段。`订单 20138123456789012` 里的 11 位片段不会被误判。

### 3.2 第二道 —— 校验算法

| 类型 | 算法 | 效果（实测） |
|------|------|-------------|
| 身份证 | GB 11643-1999 校验码 + 出生日期合理性 | 200 个校验位错的号**全部排除** |
| 银行卡 | Luhn（ISO/IEC 7812） | 200 个 Luhn 不过的号**全部排除** |

**没有校验位这 400 条会全部误报** —— 正则本身都匹配。基准脚本第 3 步专门验证这一点。

### 3.3 第三道 —— BIN 前缀 + 法定长度

这道是实测逼出来的。Luhn 是 10 取模，**随机数字串约 1/10 概率碰巧通过** —— 首轮基准里 400 条随机数字负样本有 20+ 条过了 Luhn，误报率 6.75%。

加上"发卡行 BIN 前缀 + 该卡种法定长度"约束：

```python
if p1 == "4":                       return n in (13, 16, 19)   # Visa
if p2 in {"51",...,"55"}:           return n == 16             # Mastercard
if p2 == "62":                      return 16 <= n <= 19       # 银联
if p2 in {"34", "37"}:              return n == 15             # AmEx
```

误报率从 **6.75% 降到 0.75%**。这也是真实 DLP 产品的做法。

### 3.4 跨类型消歧

同一串数字可能匹配多种类型，规则：

| 冲突 | 处理 | 理由 |
|------|------|------|
| 11 位以 1 开头 | 判手机号，不判银行卡 | 手机号形态更确定 |
| 18 位含合法出生日期 | 判身份证形态，不判银行卡 | Luhn 有 1/10 碰巧通过率 |
| 17 位紧跟 `X`/`x` | 跳过 | 是身份证被银行卡正则截断的前半段 |
| 区间重叠 | 取更长、再取高置信度、再取高敏感级 | 身份证 18 位应盖过其中的短片段 |

## 4. 姓名启发式的两次修正

姓名是唯一没有校验算法可依的类型，做了两轮修正：

**第一轮问题** —— 正则带右侧 lookahead `(?![一-龥])`：

```
"患者陈芳于今日就诊"  → 姓名后紧跟中文，整体失配 → 漏检
```

去掉 lookahead 后能匹配，但会**多吃字**：捕获到 `陈芳于今`。

**第二轮方案** —— 捕获 2-4 字后由 `_trim_name` 从长到短试：

1. 首字必须在姓氏表里（覆盖大陆人口约 95% 的常见姓氏），否则整体判否
2. 后续字含虚词（`于是的已在与和就将...`）说明多吃了，试更短的
3. 命中停用词（`测试`/`数据`/`系统`...）跳过

姓名召回从 83% → 87.5% → **100%**。

写这份姓氏表时把 `single` 这个词误粘进了字符串中间，导致 `郭`/`黄`/`林` 等常见姓氏缺失 —— 已重整为按第七次人口普查常见姓氏排列的表。

## 5. 脱敏与还原

```python
r = scanner.scan_and_mask("电话 13812345678 邮箱 a@example.com")
# r.masked_text: "电话 [PII-手机号-001] 邮箱 [PII-邮箱-001]"
# r.mask_map:    {"[PII-手机号-001]": "13812345678", ...}

PIIScanner.unmask(r.masked_text, r.mask_map)  # 完整还原
```

占位符按类型独立编号（`手机号-001`、`手机号-002`），便于人读。`mask_map` 是 DLP-08 在最终输出还原的依据 —— **仅限同一 session**，跨 session 的占位符不在表中，保持原样不还原（防跨会话信息泄露）。

## 8. 已知边界

1. **姓名依赖称谓上下文** — 无 NER 时，`报告作者是李娜` 这类无称谓词的姓名抓不到。接入 NER 后端可解
2. **地址仅覆盖大陆行政区划格式** — 海外地址、简写地址（`朝阳区建国路88号`，缺市级）不匹配
3. **医疗召回 98%** — 病名词表有限，罕见病名未覆盖。词表可扩展
4. **BIN 库是卡种级而非发卡行级** — 见 §6.4，残留 0.75% 误报的根因
5. **无上下文语义判断** — `13812345678` 在"手机号"和"随机测试数据"语境下同等对待。语义级判断需 LLM，代价与收益需评估
6. **仅中文优化** — 英文姓名、国际电话号码格式未覆盖

### 10.1 策略存储：四级回退

`(agent_id, pii_type)` 为主键，查询逐级回退：

```
(agent, type) → (agent, *) → (*, type) → (*, *) → 系统兜底
```

一条 SQL 把四种组合都取回来，再在内存里按优先级挑 —— 避免四次查询。

**系统兜底按风险级分档**，不是一刀切：

| 风险级 | 兜底动作 | 理由 |
|--------|---------|------|
| L1/L2（姓名、邮箱、手机、地址） | `audit_only` | 默认拦会打断正常业务（通讯录助手连电话都读不到） |
| L3/L4（身份证、银行卡、医疗、生物特征） | `mask` | 高敏 PII 默认就不该原样流转 |

四种动作：`allow`（放行不记录）、`audit_only`（放行记审计）、`mask`（脱敏后继续）、`block`（拒绝）。

manifest `[dlp]` 节导入时，`default`/`*` 映射到通配键；**拼错的类型名与非法动作静默跳过** —— 配置写错不该让 Agent 起不来，那条规则不生效即可。

### 10.2 DLP-03 输入过滤：只脱该脱的

同一段文本里不同类型可有不同处置。`_mask_subset()` 只脱 `mask`/`block` 类型，`audit_only` 的保持原文：

```
输入："姓名：张伟，电话 13812345678，身份证 110101199003076173"
策略：name/phone = audit_only，id_card = mask
输出："姓名：张伟，电话 13812345678，身份证 [PII-身份证-001]"
```

无脑全脱会破坏业务语义 —— 姓名策略是 `audit_only` 却把姓名脱了，Agent 就没法正常对话。

多类型命中取**最严处置**（`BLOCK > MASK > AUDIT_ONLY > ALLOW`）。

脱敏映射表进 `DLPSessionStore`（内存、按 session 隔离、不落盘），供 DLP-08 还原。`get()` 返回副本，外部改动不污染内部状态。

### 10.3 DLP-04 云端阻断：高敏不出本机

核心规则：**云端调用 + L3/L4 PII → 强制脱敏，覆盖 audit_only 策略**。

| 场景 | 结果 |
|------|------|
| 本地 + L3 + `audit_only` | ALLOW（不出网，可接受原文） |
| 云端 + L3 + `audit_only` | **MODIFY 强制脱敏**（标 `cloud_forced_mask`） |
| 云端 + L3 + `block` | BLOCK |
| 云端 + 仅 L1/L2 | 按策略走，不强制 |

强制脱敏而非直接拒绝，是为了让云端推理仍然可用 —— 脱敏后的 prompt 出网不泄露，模型照样能回答。

云端判定：`context["is_cloud"]` 显式指定优先；否则按 endpoint 推断，`localhost`/`127.0.0.1`/`::1`/`unix:` 视为本地。**无 endpoint 信息时按本地处理** —— 保守放行，不误拦本地推理。

### 10.4 接入时暴露的两个框架缺陷

DLP handler 是干预点框架的第一批真实使用者，接入过程暴露了两个只有实际用起来才会发现的问题。两处都补了回归测试。

**其一：MODIFY 决策被吞掉。**

原实现把 MODIFY 用于链式传递，但最终决策仍报 ALLOW。调用方看到 ALLOW 就继续用原始数据 —— **脱敏白做了**。

修正后优先级：`BLOCK`（短路） > `CONFIRM` > `MODIFY` > `ALLOW`。CONFIRM 压过 MODIFY 时，改写结果仍从 `modified_data` 带出。

**其二：handler 的 metadata 被丢弃。**

`invoke()` 只把 `_handler_trace` 放进结果，各 handler 自己设的 `pii_types`、`max_risk`、`is_cloud`、`cloud_forced_mask`、`dlp_policies_loaded` 全部丢失。DLP-10 的 WebUI 统计和审计都要读这些字段。

修正为按执行顺序合并（后者覆盖同名键），**BLOCK 短路时也带上此前 handler 的 metadata** —— 被拒的调用最需要完整上下文。

这个缺陷是 `dlp_e2e.py` 发现的：单测各自验证 handler 返回值，都过；只有端到端经 `registry.invoke()` 才暴露出字段在框架层丢了。

### 11.1 DLP-05 两类风险分开处理

| 风险 | 处置 | 是否受 PII 策略影响 |
|------|------|-------------------|
| 输出含 PII | 按策略 mask/block/audit_only | 是 |
| 逐字复现训练语料 | **一律 BLOCK + 告警** | **否** |

逐字泄露是模型行为异常（记忆泄露），不是数据敏感度问题 —— 即使把 8 类 PII 策略全设为 `allow`，泄露仍拦。检测顺序上泄露优先，命中即短路。

### 11.2 逐字泄露检测：双信号，因为单用覆盖率能被绕过

**首版只用覆盖率**（输出 n-gram 被语料覆盖的比例），实测发现可以"补长"绕过：

| 尾部追加无关文本 | 输出 n-gram 数 | 覆盖率 | 判定 |
|-----------------|--------------|--------|------|
| 0 字 | 45 | 100% | 拦 |
| **15 字** | 58 | **77.6%** | **漏** |
| 66 字 | 86 | 52.3% | 漏 |

（语料样本归一化后 64 字，门限 0.8）

分母随输出增长，比例天然被稀释 —— 抄完整段原文再拼十几个字就能滑到门限下。

改为**双信号，任一命中即判泄露**：

1. **绝对连续长度 ≥ `min_span`（默认 100 字）** —— 主信号。抄了 100+ 字连续原文就是泄露，后面拼多少自有内容都不改变这个事实
2. **覆盖率 ≥ `threshold`（默认 0.8）** —— 辅助信号，兜住短于 `min_span` 但通篇照抄的情况

`_longest_common_span()` 先用 n-gram 找锚点、再向右贪心延伸求最长连续匹配。本场景文本量下够用，不必上后缀自动机。

两个门限均可经 context 调（`dlp_leak_min_span` / `dlp_leak_threshold`）。

用覆盖率而非 Jaccard 的理由：语料通常远长于输出，Jaccard 的分母被语料撑大，短输出即使整段照抄也算不出高分。

### 11.3 DLP-06 工具参数：提升 CONFIRM 而不脱敏

工具参数里的 PII **不能脱** —— 脱了工具就没法用：路径里的手机号被换成占位符会导致文件找不到，API body 里的身份证被脱会让请求失败。

所以改为**提升决策为 CONFIRM**，让用户明确批准把 PII 交给这个工具；批准后工具拿到的仍是原始参数。

| 策略 | input 干预点 | pre_tool_call 干预点 |
|------|-------------|---------------------|
| `allow` | 放行 | 放行（明确豁免） |
| `audit_only` | 放行记审计 | **提升 CONFIRM** |
| `mask` | 脱敏 | **提升 CONFIRM** |
| `block` | 拒绝 | 拒绝 |

`audit_only` 在这里也提升 —— 工具调用意味着 PII 要离开 Agent 进程（写文件、发网络请求），比留在上下文里高一档风险。

参数序列化容错：`json.dumps(..., default=str)`，再失败退 `str()` —— 参数形态不定，不能因为序列化失败就扫不到。

### 11.4 与 SEC capability 的协同

两个用例锁住协同语义：

- `test_sec_deny_shortcuts_dlp_scan` —— SEC(10) 判 DENY 时短路，DLP(50) **不执行**（trace 只有 `["sec"]`，metadata 无 `pii_source`），省掉 PII 扫描开销
- `test_sec_allow_then_dlp_confirm` —— SEC ALLOW + DLP 检出 PII → 最终 **CONFIRM**，trace 为 `["sec", "dlp_pre_tool"]`。这正是 DLP-06 的核心机制

## 12. DLP-07/08/09 — 返回值脱敏、输出审查、session 清零

| 需求 | 干预点 | 状态 |
|------|--------|------|
| DLP-07 | `post_tool_call` | ✅ 已验证 |
| DLP-08 | `output` | ✅ 已验证 |
| DLP-09 | `agent_shutdown` | ✅ 已验证 |

测试：`test_dlp_final.py`(29)；全量 **271 passed**，**8 个干预点全覆盖**

### 12.1 DLP-07 与 DLP-06 的处置方向相反

| | pre_tool_call（DLP-06） | post_tool_call（DLP-07） |
|---|---|---|
| 处置 | **提升 CONFIRM，不脱** | **必须脱** |
| 理由 | 脱了工具没法用（路径/API 参数失效） | 返回值只给模型看，脱敏不影响功能 |
| 不做的后果 | — | PII 进上下文后多轮传播，模型可能复述到最终输出 |

`payload_bytes` 记录载荷大小，供 ARCH-01 判是否该走 UDS（>4 KB）。

### 12.2 DLP-08 输出审查三步

**① 还原本 session 占位符** —— DLP-03/07 脱敏是为了不让 PII 在 Agent 内部传播，但**用户本来就有权看自己提供的信息**。仅还原本 session 映射表里的占位符，跨 session 的不还原（防会话间泄露）。

**② 还原后复扫** —— 还原可能把新 PII 暴露出来（如策略在会话中途改严）。

**③ 处置 + 可选水印**：

- `block` 策略下整体替换为 `[内容已屏蔽：含 ...]`，**不直接 BLOCK** —— 用户会看到空响应，不知道发生了什么
- 水印用零宽字符（ZWSP/ZWNJ 编码 payload，ZWJ 作边界），视觉不可见，`extract_watermark()` 可提取溯源

**MODIFY 的判定依据是"是否发生过处理"，不是"最终文本是否等于原文"**：还原 → 复扫 → 重新脱敏会产生与原文逐字相同的串（占位符编号一致），此时若报 ALLOW，调用方就不知道中间还原过明文 PII，`restored_placeholders` 审计字段也被埋掉。这是测试 `test_output_rescans_after_restore` 发现的。

### 12.3 DLP-09 清零

退出是终态，拦也没意义 —— 只观察 + 清理。清掉 session 内的脱敏映射表（含明文 PII），返回清理条数供审计。

### 12.4 8 个干预点闭环

```

input           dlp_input        输入过滤（选择性脱敏）

post_model_call dlp_post_model   输出 PII + 逐字泄露检测

post_tool_call  dlp_post_tool    返回值脱敏

```

### 13.2 矩阵的"显式/继承"标记是必要的

用户需要区分"我显式配置的"和"从系统兜底继承的"：

- **显式配置**：可点"恢复默认"按钮删除，回到兜底
- **继承/兜底**：灰色显示，`source: "inherited"`，不显示删除按钮

如果全部展示为同一样式，用户不知道哪里改过，哪里是默认。

### 13.3 两个修复（路由实测暴露）

1. **非法 action 返回 500 → 400** —— `ValueError` 是客户端输入错误，`_err(e)` 给 500 是误用；改为在内层 catch `ValueError` 后明确返回 400
2. **stats D-Bus 不可达返回 500 → 200 + 降级数据** —— DLP 策略配置不依赖 D-Bus，不该因为统计取不到就让整个 DLP 页打不开；改为返回 `{"degraded":true, "reason":"..."}` 让前端展示"统计不可用"
